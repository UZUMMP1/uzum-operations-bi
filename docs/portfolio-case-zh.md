# 项目案例｜UZUM 运营 BI：从手工报表到经营决策系统

> 作品集版本。所有数据、日期、截图与动图均为脱敏或虚构演示内容。

## 项目背景

我所在的电商运营场景需要每日在固定时间前完成上一日销售记录，并持续更新库存 PSI 表。原始数据分布在销售、库存和流量底表中；库存与流量往往只能逐日下载，因此除了更新当日数据，还要持续留存日级历史快照。

原有工作流高度依赖 Excel、VLOOKUP 和人工核对：计算 SO、GMV、ASP、UV、CVR，更新库存、14 日均销、DOS 和补货建议，分析取消/退货，并在每周盘点时把供货、累计销量、现有库存与异常事件重新对齐。单次完整更新通常需要 4 小时以上，且难以直观回看趋势或快速定位异常原因。

项目目标不是做一张“漂亮的仪表盘”，而是建立一个可以稳定回答以下问题的经营系统：

- 昨天的销量为什么变化，今天最需要处理什么？
- 增长或下降由哪些 SKU、品类、流量、转化或库存因素造成？
- 哪些 SKU 需要补货、可能断货或已经滞销？
- 取消和退货分别集中在哪些商品，应该怎样继续排查？
- 供货、销量和库存为什么对不上，哪些差额可以被近期事件解释？

## 项目进行过程

### 第一阶段：梳理业务工作流与信息架构

我没有直接按已有报表搭页面，而是先拆分运营人员每天、每周和盘点时真正要完成的任务。基于日报、PSI、销量归因、售后、盘点和周期复盘的不同逻辑，最终形成 8 个板块：

1. 经营总览：日级 KPI、品类和 SKU 表现、每日诊断；
2. 销售趋势：按日期、品类和 SKU 观察 SO、GMV、UV、CVR、ASP；
3. 退货/取消：拆分售后事件、趋势和 TOP SKU；
4. 库存 PSI：库存快照、DOS、补货、滞销和推算入库；
5. 库存盘点：供货、销量、库存和取消/退货事件的进销存核对；
6. 运营洞察：数据质量检查与经营信号；
7. 运营 Agent：固定问题的可追溯分析与建议；
8. 日报/周报：将筛选条件下的分析结果标准化输出。

### 第二阶段：对齐数据与指标口径

我梳理销售、库存、流量、供货和商品映射表，建立跨表关联所需的条形码、SKU、小米 ID 和产品属性关系，并确定核心口径：

- 实际 SO = 数量 − 取消/退货；SO（不去退）= 数量；
- ASP = GMV ÷ 实际 SO；UV 使用“详情页打开次数”代理；
- CVR = 在日期与 SKU 均匹配流量的前提下，SO（不去退）÷ UV；
- 业务库存日 D 对应原始库存 DATE=D+1，避免将错误快照当作期末库存；
- 14 日均销按 14 个自然日固定计算，DOS=当前在售库存÷14 日均销；
- 盘点差额=实际供货量−（最新现有库存+建店至今实际 SO）。

### 第三阶段：验证、迭代与产品化

搭建后，我先用业务数据逐项对比原始 Excel 和人工计算结果，重点核对日期范围、库存边界、取消/退货分类、CVR 分子与分母、盘点差额等高风险部分。对于发现的偏差，先定位口径与字段映射问题，再调整产品规则。

在基础看板稳定后，我进一步把高频分析做成规则型 Agent，把人工“看完数据再想下一步”的过程，转化为带数据范围、依据和建议的标准流程。

## 项目进行中的卡点

### 1. 库存与流量缺少可回溯的历史数据

平台无法像销售数据一样一次性下载所有历史日期的库存和流量，因此仅看当天文件无法判断趋势。我将数据设计为日级快照留存，并在分析中明确区分“业务日”和原始下载日期，避免日期错位。

### 2. 源数据口径与人工表格可能不一致

看板能显示不代表口径正确。特别是在退货、库存快照和 CVR 上，一个日期或字段误差都会放大为错误结论。我用业务数据逐条对账，在设计阶段就把“与人工核算一致”作为验收条件。

### 3. 进销存差额不等于一个简单的“丢货”结论

供货、销量和库存不一致时，可能是供货未录入、条形码映射缺失、库存回流滞后、取消/退货未回库、调拨或文件日期错误。我没有把差额直接解释为异常，而是保留最近事件、分类原因并交给业务人员继续核实。

### 4. 自动化下载可能出现空表或不完整数据

AI 自动下载并不能自动保证数据可用。平台卡顿时可能只下载到表头或缺少日期；若直接进入计算，会产生看似合理但错误的结论。因此系统增加数据质量与上传历史：检查空文件、行数变化、缺失日期、日期错位、重复上传和漏传来源。

### 5. AI 开发对话记录丢失

调试阶段，长对话记录意外消失。我只能根据现有页面、代码与输出反向还原大部分运算规则。这让我意识到聊天记录不是可靠的项目文档，因此补充了数据口径、操作手册、风险清单和接管规则。

## 项目复盘

### 业务与产品层面

最重要的收获是：运营 BI 的价值不在于指标数量，而在于能否把指标放进决策顺序。一个有效的日常流程应当是“数据质量确认 → 经营变化定位 → SKU/品类归因 → 库存与售后验证 → 明确当天动作”，而不是让使用者在多个图表中自行猜测。

### AI 使用层面

AI 适合加速代码和重复分析，但不能代替数据口径、业务边界和验收。这个项目中，AI 生成的结果必须回到实际数据与人工表格中验证；遇到缺失数据时，系统应提示不确定性，而不是补出一个看似准确的答案。

### 后续迭代方向

- 增加更严格的自动下载成功判定和异常告警；
- 统一不同页面中 CVR 的日期+SKU 精确匹配逻辑；
- 在规则型预警基础上加入统计异常检测与补货预测；
- 完善取消/退货回流、调拨和盘盈盘亏的事件链路；
- 增加权限控制和更精细的数据访问边界。

## 我的职责

我负责业务问题定义、需求拆分、字段关系梳理、核心指标口径、页面信息架构、Agent 工作流、数据验证、边界条件测试、隐私设计和交接文档。AI 用于辅助实现和加快迭代，但产品是否满足业务需要、计算是否可信、哪些功能应该上线，均由我做出判断与验收。
